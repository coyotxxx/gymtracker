**Data:** 2026-06-10

## 1. STRESZCZENIE

**Co działa dobrze (fundamenty są):**
- Override „tylko bieżnia" respektowany wzorcowo (sekcja UWAGI UŻYTKOWNIKA — WYMÓG w prompcie WorkoutPlanAi).
- Matematyka dietetyka solidna: TDEE Mifflin-St Jeor, `SafetyGuard` (kcal floor = BMR, protein/fat min-max), 8 typów celów `DietGoalType`, `CalorieAdjustmentEngine` regułowy, refeed/diet-break phase-aware (`PhaseManager`).
- Deload + periodyzacja — reaktywne, ale **akcjonowalne** (przyciski „Zastosuj").
- Infrastruktura realnej konsumpcji istnieje: `MealReminderWorker` z akcjami „Zjedzone/Pominięte" → zapis do `MealConsumption`.
- `MasterAiContextBuilder` — AI dostaje wspólny, spójny kontekst trener+dietetyk.

**Co wymaga pracy (rdzeń wizji niespełniony):**
- **Adherence diety liczy PLAN, nie realną konsumpcję** → fałszywe 99-100% przez miesiąc, co dodatkowo blokuje auto-korekty kcal.
- **Brak detektora „zaplanowany trening niewykonany"** → 15× zaplanowane / 3× zrobione = zero reakcji.
- **Raport tygodniowy bez schedulera** → 27 dni zastoju, tylko ręczny przycisk.
- **Warstwa proaktywna faktycznie martwa** → `aiProactiveChecksEnabled=false` domyślnie + alerty trenera liczone tylko przy renderze ekranu Home.
- **Trener i dietetyk działają w silosach** — AI dostaje pełny obraz, ale deterministyczne silniki nie czytają się nawzajem (np. INTENSIFICATION + CUT bez ostrzeżenia).

**Wniosek:**
Wszystkie cegły istnieją (analyzery, workery, MealConsumption, MasterContext, phase linkage). Brakuje **klucza sklepień**: proaktywnej warstwy coachingu w tle (`CoachEngine`), która sama robi dzienny snapshot, podejmuje decyzję i powiadamia — niezależnie od tego, czy user otworzył apkę — oraz spięcia adherence z realną konsumpcją i deterministycznych silników ze sobą. Plan w sekcjach 6-7.

## 3. PRZYCZYNA ŹRÓDŁOWA

> **Aplikacja jest zbudowana REAKTYWNIE — czeka aż user otworzy apkę (a konkretnie ekran Home). Trener i dietetyk personalny działają PROAKTYWNIE.**

Ten jeden korzeń tłumaczy prawie każdą lukę:
- Raport tygodniowy: tylko ręczny przycisk (`WeeklyReportScreen.kt:117`).
- Alerty trenera: liczone wyłącznie przy renderze Home (`HomeViewModel.kt:221` → `HomeAlertNotifier`). Gdy user patrzy na Dietę/Statystyki — cisza.
- Opuszczony trening: brak jakiegokolwiek detektora.
- Adherence diety: przelicza się tylko przy add/delete posiłku, nie przy oznaczeniu konsumpcji.
- Długa przerwa: wykrywana dopiero po powrocie.

**Lekarstwo (north star):** proaktywny `CoachEngine` — periodyczny worker (WorkManager) robiący raz dziennie snapshot (adherence treningu, realna konsumpcja, waga, regeneracja, nawodnienie, HRV), podejmujący decyzję (alert? akcja? korekta?) i powiadamiający w tle. Trener i dietetyk czytają to samo źródło i nawzajem swoje sygnały.

## 4. AUDYT PER FILAR

### 4.1. Dietetyk — liczenie adherence

**Jak działa dziś:**
- `AdherenceCalculator.computeForDate()` (`AdherenceCalculator.kt:33-105`): linia 51 pobiera `meal_entries` (plan), linia 52 pobiera `meal_consumptions` (status), linie 53-56 budują `skippedTypes`, linie 65-74 sumują kcal pomijając mealType z `skippedTypes`.
- Recompute wyzwalane z `DietViewModel` przy `addMeal()`/`deleteMeal()` (`DietViewModel.kt:1136,1143,1161`) oraz `AdherenceReportViewModel.computeForToday()` w init.

**Bug (plik:linia):**
1. **`cycleConsumption()` nie wyzwala recompute** — `DietViewModel.kt:147-152`: woła `consumptionRepo.cycleStatus()` + `refreshConsumptions()`, ale **nie** `adherenceCalc.computeForDate()`. Oznaczenie „pominąłem obiad" zmienia status w UI, ale adherence zostaje stara.
2. **Puste consumptions = liczone wszystkie meal_entries** — `AdherenceCalculator.kt:52`: gdy user nigdy nie kliknął konsumpcji, `consumptions=[]` → `skippedTypes=∅` → linia 66 nigdy nie pomija żadnego wpisu → adherence = plan/plan = ~100%.

**Skutek łańcuchowy:** `CalorieAdjustmentEngine.analyze()` (`CalorieAdjustmentEngine.kt:75`) bierze fałszywą adherence ≥85% jako input → **nigdy nie zaproponuje korekty kcal**.

**Jak powinno:** `actualKcal` = suma posiłków faktycznie zjedzonych. CONSUMED → pełne kcal; SKIPPED → 0; brak statusu/PLANNED → traktować jak niezjedzone (0) **albo** wymusić oznaczenie. Recompute MUSI odpalać się po każdej zmianie statusu konsumpcji. Decyzja semantyczna do podjęcia: czy `PLANNED` (zaplanowany, nieoznaczony) liczy się jako 0, czy jako zjedzony — patrz sekcja 8.

**Konsumenci adherence:** `AdherenceReportScreen.kt:186-214`, `CalorieAdjustmentEngine.kt:75`, `MasterAiContextBuilder` (prompt AI), `WeeklyReportService`.

### 4.2. Dietetyk — cele i ochrona zdrowia

**Jak działa dziś (fundamenty mocne):**
- TDEE Mifflin-St Jeor + mnożnik aktywności + bonus cardio (`DietGoals.kt:65-105`).
- 8 typów celów + deficyt z defaultami (`DietGoals.kt:107-158`).
- `SafetyGuard` (`SafetyGuard.kt:17-139`): kcal floor = max(absolut, BMR), kcal ceil 80×kg, protein 1.4×kg (aktywni) / 0.8 (sedentary), fat min 0.6×kg.
- `CalorieAdjustmentEngine` rekalkuluje co 14 dni / na żądanie: fast-loss → +150, stagnacja+high adherence → -150, wczesny plateau 7d → -100, refeed/diet-break (`PhaseManager.kt:85-194`).
- Recovery-aware: zły sen+stres → HOLD; głód → REFEED; soreness+low energy → DELOAD (`CalorieAdjustmentEngine.kt:118-193`).
- Hydration blokuje cięcie kcal przy <60% (`CalorieAdjustmentEngine.kt:182-191`).

**Luki/bugi (plik:linia):**
- **L-D1** Tempo redukcji >1.5 kg/tydz = tylko WARNING, nie BLOCK — `SafetyGuard.kt:111`.
- **L-D2** Protein floor nie sprawdzany w auto-korekcie — `AutoAdjustmentService.kt:112` waliduje tylko kcal; -kcal może zbić białko poniżej minimum.
- **L-D3** 0 pomiarów wagi → silnik zwraca `NEEDS_MORE_DATA` i **czeka w ciszy** — `CalorieAdjustmentEngine.kt:95`. Brak monitu „zważ się".
- **L-D4** Hydration: próg 60% za niski, brak proaktywnego alertu przy 62-75% — `CalorieAdjustmentEngine.kt:182`.
- **L-D5** Refeed/diet-break to opcjonalne dialogi — user może ignorować 2 tyg. (brak notyfikacji/auto-apply).
- **L-D6** RHR/HRV degradation tylko jako info, nie wpływa na rady dietetyka przy BULK — `RecoveryAnalyzer.kt:105-114`.

**Jak powinno:** trójwarstwowo — MATH (jest) → MONITORING (proaktywny dzienny check: ważenie? nawodnienie? białko? RHR?) → DECISION+EXECUTION (sugestia → notyfikacja → opcja zero-click apply). Dietetyk sam się odzywa, nie czeka na otwarcie ekranu „Sprawdzenie".

### 4.3. Raport tygodniowy

**Jak działa dziś:**
- Wiersz w `ai_weekly_reports` tworzy wyłącznie `WeeklyReportService.generate()` (`WeeklyReportService.kt:413`).
- Jedyny trigger: ręczny przycisk `WeeklyReportScreen.kt:116-121` → `WeeklyReportViewModel.generate()`.

**Dlaczego stoi 27 dni (plik:linia):**
- **Brak `WeeklyReportScheduler`/`WeeklyReportWorker`** — `WorkerRescheduler.rescheduleAll()` (`WorkerRescheduler.kt:36-51`) planuje `ProactiveAiCheck` i `DietAutoAdjustment`, ale NIE raport tygodniowy.
- Dedup `AiWeeklyReportDao.getForWeek()` (`AiWeeklyReportDao.kt:19-20`) **istnieje, ale nieużywany** w `generate()`.
- Brak flagi `aiAutoGenerateWeeklyReports` w `UserProfile`.
- Brak notyfikacji „raport gotowy".

**Jak powinno:** `WeeklyReportWorker` (periodic 7 dni, niedziela wieczór) → guard `getForWeek()` → `generate()` → notyfikacja + flaga w profilu + wpięcie w `WorkerRescheduler`.

### 4.4. Trener — monitorowanie i proaktywność

**Jak działa dziś:**
- `HomeAlertNotifier.maybeNotify()` (`HomeAlertNotifier.kt:39-59`) wołane z `HomeViewModel.kt:221` przy każdym renderze Home; anti-spam po hashu; per-type dismiss.
- `DeloadService.cardState()` (`DeloadService.kt:67-101`): priorytet ActiveInjury > ReturnAfterBreak > Suggestion(deload) > None.
- `ProactiveAiCheckWorker` (periodic 24h) — reguły: ból ≥2/3 treningów, stagnacja, partia bez treningu ≥7 dni, propozycja periodyzacji.
- Deload i periodyzacja są **akcjonowalne** (przyciski „Zastosuj").

**Luki proaktywności (plik:linia):**
- **L-T1** Brak detektora „zaplanowany trening niewykonany" — `TrainingDietBridge.kt:103-117` liczy `TrainingType.SKIPPED`, ale nic tego nie czyta do alertu. Brak `onMissedWorkout()`.
- **L-T2** Długa przerwa reaktywna — `DeloadDetector.kt:160` (`daysSince>=14 && sessionsLast14d==0`) czeka aż user wróci, nie czuwa w trakcie przerwy.
- **L-T3** Periodyzacja liczy tygodnie niezależnie od adherence — `PeriodizationOrchestrator.kt:50-56` (`weekInPhase = daysSinceStart/7+1`); cykl „leci" mimo opuszczonych sesji.
- **L-T4** `ReturnAfterBreak`/`ActiveInjury` bez przycisków akcji — `HomeAlertNotifier.kt:63-93` (sam deload ma „Zastosuj").

**Jak powinno:** `EventDetectorService.onDayFinished()` (~22:00) → jeśli `SKIPPED && wasTrainingPlanned` → alert „dzisiaj miał być [Plan], jutro?"; `BreakMonitoringDetector` czuwający w trakcie przerwy (7/14 dni); periodyzacja flaguje `adherenceLow` i wstrzymuje `weekInPhase`; wszystkie alerty z przyciskiem akcji.

### 4.6. Wymiana danych trener↔dietetyk

**Co JEST zintegrowane:**
- `DietPhase.linkedTrainingMesocycleId` + `trainingPhaseSnapshot` (`DietPhase.kt:53-56`), ustawiane przy starcie fazy (`DietViewModel.kt:526-540`).
- `PhaseManager.suggest()` czyta fazę treningu i skaluje refeed (INTENSIFICATION +400, DELOAD +150) — `PhaseManager.kt:64-194`.
- Carb cycling w AI-generowanych planach (`DietAiService.kt:442-451`): dni treningowe więcej węgli pre/post-WO, rest mniej.
- `HealthInsightAnalyzer` (sen/HRV → WorkoutAdjustment) wpięty w audyt planu (`PlanAuditService.kt:91`).
- Wspólne źródło celu po v1.28: `DietGoalType` canonical + `weightGoalType` auto-mirror (`UserProfile.kt:134-147`).

**Co NIE jest / rozjazdy (plik:linia):**
- **L-X1** `TrainingPhaseAnalyzer` nigdy nie czyta diety — możliwy INTENSIFICATION (trening) + CUT (dieta) **bez ostrzeżenia**.
- **L-X2** `DietPhase` nie zamyka się przy zmianie globalnego celu (snapshot, nie żywy link) — CUT→BULK zostawia starą fazę CUT aktywną.
- **L-X3** Carb cycling asymetryczny — `CalorieAdjustmentEngine` zmienia tylko sumę kcal, nigdy rozkładu makro per dzień treningowy/rest.
- **L-X4** `PeriodizationOrchestrator` nie czyta `RecoveryRepository` — brak hard-block „CUT + zły sen + HRV drop → wymuszony deload".

**Jak powinno:** deterministyczne silniki czytają się nawzajem (nie tylko AI): `PeriodizationOrchestrator.pulse()` czyta recovery+dieta; `TrainingPhaseAnalyzer` czyta cel i ostrzega o konflikcie; `CalorieAdjustmentEngine` robi carb cycling; `DietPhase` = żywy link z auto-closure przy zmianie celu.

## 8. RYZYKA I DECYZJE

**Decyzje do podjęcia z właścicielem:**
1. **Semantyka PLANNED w adherence (P0-1):** ✅ **ZDECYDOWANE (2026-06-10): posiłek nieoznaczony = NIEZJEDZONY (0 kcal).** Tylko CONSUMED liczy pełne kcal; SKIPPED i brak statusu = 0. Adherence pokazuje realne spożycie, zgodnie z wizją „dietetyk pilnuje". Konsekwencja UX: user musi oznaczać zjedzone posiłki, inaczej adherence leci w dół — rozważyć w przyszłości monit/szybkie oznaczanie zbiorcze (hybryda) jako osobne usprawnienie, nie blokuje v2.11.0.

3. **Zero-click apply korekt dietetyka:** czy sugestie (refeed, -kcal) mają być auto-aplikowane po N godzinach braku reakcji, czy zawsze wymagać „Zastosuj"?

**Ryzyka techniczne:**
- Migracje Room (v2.13, v2.16, v2.18) — bezwzględnie prawdziwa Migration(N,N+1), test ścieżki update (stary APK → install -r), bo to PRODUKCJA z danymi Macieja.
