## 1. STRESZCZENIE

**Co jest dobrze:**
- Solidna architektura MVVM + Hilt + Room + Compose Material3 + Kotlin 2.1.0
- **Hybrid AI Engine już istnieje** (v1.1.0) — algorytm liczy, AI proponuje. To fundament pod periodyzację.
- 6 analyzerów (TrainingPhase, Stagnation, ACWR, Readiness, Health, Recovery) — wszystkie z fast variantami i StatsSnapshot
- 351 testów jednostkowych pokrywających core domain (Epley PR, ACWR, MuscleRecovery decay, CalorieAdjustment)
- BYOK Claude/OpenAI z EncryptedSharedPreferences (AES-256-GCM), Tool calling, AiLog audit
- Memory Architecture 5-tier (Raw → Aggregates → Rollups → Events → MasterContext)
- Snapshot-based refactor (v1.11.42-50) wyeliminował większość N+1 queries

**Co wymaga pracy:**
- **Brak `TrainingMesocycle` entity** — periodyzacja jest computed, nie ma trackingu cyklu z datami startu/końca
- **Brak migracji Room 51→52, 52→53** + `fallbackToDestructiveMigration(true)` → ryzyko WIPE danych Macieja (3.5 lat historii) przy update
- **Hardcoded `isTodayHeavyTraining=false`** (DietViewModel:440) i `hadTrainingToday=false` (DietViewModel:564) — dieta NIGDY nie zasugeruje REFEED na heavy day
- **MainActivity nie obsługuje intent.extras** — push z workerów otwiera Home zamiast docelowego ekranu
- **DeloadService działa tylko dla świadomego deloadu** (przycisk "Zastosuj"), pasywnie wykryty deload nie ma countdown
- **Brak orkiestracji**: 6 analyzerów żyje osobno, AI nie łączy ich w decyzję cyklu
- Inline kolory (51 instancji `Color(0xFF...)`) zamiast theme tokens
- 3 dead Composables w workout (BigMetricCard, ContextCard, SuggestionCard)
- Health Connect 1.1.0-alpha07 + Security Crypto 1.1.0-alpha06 = **alpha biblioteki na produkcji**

**Wniosek:**
Aplikacja jest **gotowa na refaktor periodyzacji**. Wszystkie cegły istnieją: analyzery, event timeline, period rollups, AI z tool calling. Brakuje **klucza sklepień** — entity `TrainingMesocycle` + orkiestratora `PeriodizationOrchestrator` + UI z osią czasu. Plan w sekcji 7.

- Activity: no workouts 5-30d, no body weight 10-60d

**Filozofia:** Hybrid AI Engine rozszerzony na periodyzację:
- **Algorytm = księgowy.** Twarde fakty: "tydzień 6/6 intensyfikacji", "ostatni deload 47 dni temu", "ACWR 1.6", "RPE rośnie".

- **User = wykonawca.** Widzi konkret z buttonami, nie analizę.

**Roadmap: v1.13.0 → v1.20.0 (8 release'ów).**

// data/entity/TrainingMesocycle.kt
@Entity(tableName = "training_mesocycles", indices = [
    Index("startDateMs"),
    Index("status")
])
data class TrainingMesocycle(
    @PrimaryKey(autoGenerate = true) val id: Long = 0,
    val startDateMs: Long,
    val endDateMs: Long? = null,        // null = jeszcze trwa
    val plannedEndDateMs: Long,
    val phase: MesocyclePhase,           // ACCUMULATION / INTENSIFICATION / DELOAD / PEAKING / RECOVERY
    val weekInPhase: Int = 1,
    val phaseLengthWeeks: Int = 3,
    val trainingPlanId: Long? = null,
    val volumeProgression: Double = 1.0, // scale factor
    val intensityProgression: Double = 1.0,
    val targetRpe: Int = 8,
    val triggerReason: String = "",      // dlaczego ta faza
    val aiAcceptedDecision: String = "", // AI uzasadnienie
    val aiConfidence: Double? = null,
    val status: MesocycleStatus = MesocycleStatus.PLANNED, // PLANNED / ACTIVE / COMPLETED / SKIPPED
    val notes: String = "",
    val createdAt: Long = System.currentTimeMillis()
) {
    val isActive: Boolean get() = status == MesocycleStatus.ACTIVE
    fun daysRemaining(nowMs: Long): Int = ((plannedEndDateMs - nowMs) / (24L * 3600 * 1000)).toInt().coerceAtLeast(0)
    fun daysSinceStart(nowMs: Long): Int = ((nowMs - startDateMs) / (24L * 3600 * 1000)).toInt().coerceAtLeast(0)
}

enum class MesocyclePhase {
    ACCUMULATION, INTENSIFICATION, DELOAD, PEAKING, RECOVERY
}

enum class MesocycleStatus {
    PLANNED, ACTIVE, COMPLETED, SKIPPED
}

    suspend fun pulse(): PeriodizationState {
        val active = mesoDao.getActive()
        val now = System.currentTimeMillis()
        
        if (active == null) {
            // Brak aktywnego cyklu — start nowy z bieżącego TrainingPhase
            val computed = phaseAnalyzer.analyze()
            return startNewMesocycle(computed.phase, now)

        val weekInPhase = (daysSinceStart / 7) + 1

## 10. RYZYKA I DECYZJE

### Ryzyko 1: Migracja v51→v53 — utrata danych Macieja

**Scenariusz:** Maciej ma bazę v49 (start aplikacji), aktualizuje od razu do v1.13.0 (v54). Każda migracja musi być executable.

**Mitigation:**
- Test każdej migracji z MigrationTestHelper i fixturem v49
- Backup baseline `gymtracker-backup-pre-v1.13.0.zip` przed release
- Komunikat w UpdateCard: "v1.13.0: dodano periodyzację. Zalecany backup."
- Rollback path: tag `v1.12.x-stable-baseline`

### Ryzyko 2: PeriodizationOrchestrator confluct z DeloadService

**Scenariusz:** User klika "Zastosuj deload" (świat B) jednocześnie z aktywnym TrainingMesocycle (świat A).

**Decyzja:**
- DeloadService.apply() **synchronizuje** się z orchestratorem: jeśli aktywny meso z fazą DELOAD, dziedziczy parametry; inaczej tworzy ad-hoc deload.
- Orchestrator.pulse() **respektuje** aktywny DeloadService state — nie nadpisuje user-driven decyzji.

### Ryzyko 3: AI prompt size eksplozja

**Scenariusz:** AiContextBuilder buduje 50-100KB JSON, dodanie periodyzacji rozszerza go do 150-200KB. Long conversations → rate limit / cost.

**Mitigation:**
- PeriodizationPromptHelper jest **opcjonalny** — dodawany tylko gdy `isPlanRelatedPrompt() || hasPendingDecision`
- Cache snapshot per session (TTL 5min)
- Token budget per model — sprawdzaj przed wysłaniem

### Ryzyko 4: User confusion (zbyt dużo automatu)

**Scenariusz:** AI sugeruje deload, user nie rozumie dlaczego, czuje że aplikacja "decyduje za niego".

**Mitigation:**
- **Karta "AI proponuje" ZAWSZE z buttonem "Wyjaśnij dlaczego"** — pełna transparentność algorytm + AI reasoning
- **Domyślnie: AI tylko proponuje, user musi explicit accept** (zgodnie z [memory](../../.claude/projects/-home-debian/memory/gymtracker_ai_trainer_philosophy.md))
- TrainingSettings: toggle "Auto-apply AI decisions" (default OFF)

### Ryzyko 5: Test coverage spada przy refaktorze

**Mitigation:**
- Każdy release v1.13-v1.20 dodaje **testy przed kodem** (TDD-style)
- CI fail jeśli test count < 351 (lub coverage % spada)

### Decyzja 1: Backfill historyczny — kiedy?

**Opcja A:** Przy pierwszym otwarciu po v1.13.0 — może spowolnić startup.
**Opcja B:** W tle przy idle (po splash) — preferred.
**Opcja C:** Manualnie z TrainingSettings — "Rekonstruuj historię cykli".

**Wybór:** Hybrid. Auto-backfill ostatnich 12 tyg po splash (B), reszta dostępna manualnie (C).

### Decyzja 2: Nazewnictwo fazy w UI

**Opcje:**
- "Akumulacja / Intensyfikacja / Deload" (techniczne, ale standardowe)
- "Budowa / Siła / Reset" (przystępne, mniej precyzyjne)
- Toggle w settings: technical vs casual

**Wybór:** Techniczne + InfoIcon prowadzi do Glossary z wyjaśnieniem.
